== Glossary

[cols="1,3", options="header"]
|===
|Term |Definition

|ADR |Architecture Decision Record — a short document capturing a significant architectural choice, the context that prompted it, and the alternatives considered
|Audit Ledger |An append-only, tamper-evident log of every state transition within the platform; the digital equivalent of the paper trail currently maintained through email exchanges
|CAPEX |Capital Expenditure — one-time development and infrastructure setup costs
|Counterparty |An independent insurance company that holds one or more reinsurance contracts with the client; a fully separate legal entity and external tenant on the platform
|Eligibility |The determination of which individuals in a monthly data file fall within the risk coverage of a given contract, triggering a reinsurance compensation obligation
|Hash Chain |A sequence of SHA-256 hashes where each entry incorporates the hash of the previous entry; any tampering with a historical record breaks the chain and is immediately detectable
|Longevity Risk |The financial risk borne by an insurer when insured individuals outlive actuarial expectations, requiring continued pension or annuity payments beyond the projected period
|MFA |Multi-Factor Authentication — a login requirement for a second verification step (e.g. OTP) beyond a password; required for all platform users
|MoSCoW |Prioritisation framework: Must have / Should have / Could have / Won't have
|OPEX |Operational Expenditure — recurring monthly costs for infrastructure, managed services, and licences
|Pension Portfolio |A batch of insured individuals covered under a single longevity or pension reinsurance contract, tracked as a unit in the reconciliation process
|PRA |Prudential Regulation Authority — UK regulator overseeing insurance and reinsurance firms' capital adequacy
|Reconciliation Cycle |The monthly (or periodic) end-to-end process: counterparty submits data file → reinsurer calculates eligibility → both parties negotiate and sign off on compensation
|Reinsurance |Insurance sold to insurance companies; when an insurer faces excessive longevity or pension risk, it offloads part of that risk to a reinsurer in exchange for premium payments
|RLS |Row-Level Security — a PostgreSQL feature that enforces per-tenant data access at the database layer, preventing one counterparty from accessing another's records
|Solvency II |EU/UK regulatory framework governing insurance and reinsurance capital adequacy; requires auditable, long-term records of all risk transfer transactions
|Step Functions |AWS Step Functions — a managed workflow orchestration service; used here to implement the approval state machine with built-in execution history and human-approval callbacks
|TCO |Total Cost of Ownership — full cost including development, infrastructure, and ongoing operations over a defined period
|Tenant |A single counterparty organisation on the platform; each tenant's data is strictly isolated from all other tenants
|===

== Executive Summary

=== Context

A UK-based reinsurance firm manages longevity and pension risk contracts with multiple independent insurance company counterparties. Each month, counterparties submit data files listing insured individuals still alive; the reinsurer's team applies contract rules to determine compensation, then both parties exchange proposals, negotiate adjustments, and sign off — entirely through email and Excel spreadsheets.

This manual process requires a large team of reconciliation managers. Trust between independent entities is established through repeated human verification. The client's innovation strategy seeks to automate this inter-company reconciliation, replacing manual labour with a verifiable, auditable digital platform — targeting a 2–4× reduction in reconciliation headcount while meeting UK FCA and Solvency II record-keeping obligations.

=== Scope Boundary

This engagement delivers: contract registry, counterparty file ingestion, eligibility engine, multi-step approval workflow, immutable audit ledger, multi-tenant web portal, counterparty onboarding, email notifications, and regulatory export.

This engagement explicitly *does not* include: payment service provider integration (B2B money settlement is handled outside the platform), blockchain infrastructure, historical Excel record migration (closed cycles remain in existing archives), consumer-facing functionality, or changes to the counterparties' internal systems.

|1

|Hard — changing the audit model requires data migration

|2
|How to orchestrate the multi-step approval workflow
|AWS Step Functions Standard Workflows with wait-for-callback
|Medium — Step Functions execution history is natively queryable

|3

|Easy — Cognito can be replaced without changing business logic

|5

|Easy — adding new exchange channels does not change core processing

=== Target State

A single cloud-hosted platform where the reinsurer acts as the trusted custodian. Counterparties log in, upload monthly data files through a secure portal, and review eligibility proposals computed automatically against their contract rules. A structured approval workflow replaces email chains. Every file upload, calculation, approval, and sign-off is recorded in an immutable audit ledger — providing Solvency II-grade compliance evidence without manual reconstruction.

== Option 1: Lightweight Portal

=== Overview

[cols="1,2"]
|===
|Timeline |3 months
|CAPEX |~$165K (incl. 25% contingency)
|OPEX / month |~$800
|Team |1 Architect + 2 Senior Developers + 1 QA
|Counterparty scale |Up to 5
|Audit strength |DB-level insert triggers (limited)
|===

=== What It Delivers

* Secure web portal with Cognito authentication and basic RBAC
* S3 file upload with SHA-256 checksum verification
* PostgreSQL database with audit triggers recording all inserts/updates
* Email-prompted approval (SES notification → user opens portal → approves manually)
* Basic regulatory export via SQL query

=== What It Doesn't

* Structured approval state machine — the process still relies on email discipline
* Hash-chain tamper detection — audit triggers can be bypassed by a DBA
* Automated eligibility calculation — a future investment
* Scale beyond 5 counterparties without significant re-architecture

=== Reconciliation Cycle Flow

.Happy Path — Monthly Reconciliation Cycle
[plantuml,case03-cycle-flow,format=svg]
....
@startuml
skinparam sequenceArrowType ortho

participant "Counterparty\nAdministrator" as CP
participant "Web App" as WEB

participant "S3\nFile Store" as S3
participant "Audit\nLedger" as AUDIT

participant "Reconciliation\nManager" as RM
participant "SES\nEmail" as SES

== Phase 1: File Submission ==

CP -> WEB: Upload monthly data file
WEB -> API: POST /cycles/{id}/files\n(multipart upload)
API -> S3: Store file; record SHA-256 checksum
S3 -->> API: s3_key + ETag confirmed
API -> AUDIT: INSERT FILE_UPLOADED event\n(sha256, actor, previous_hash, event_hash)
API -> SF: StartExecution — reconciliation workflow
API -->> WEB: 202 Accepted — cycle in progress

== Phase 2: Eligibility Calculation ==

SF -> EE: InvokeTask — compute eligibility\n(contract_id, data_file s3_key)
EE -> S3: Fetch data file
EE -> API: GET /contracts/{id}/rules
EE -> EE: Apply contract rules\nto each individual record
EE -->> SF: TaskSuccess — eligibility_result_json
SF -> API: POST /cycles/{id}/eligibility-result
API -> AUDIT: INSERT ELIGIBILITY_COMPUTED event\n(result_summary, engine_version, previous_hash, event_hash)
SF -> SES: Send "Proposal ready for review"\nto Reconciliation Manager

== Phase 3: Reinsurer Review ==

SES -->> RM: Email — "Cycle {id} proposal ready"
RM -> WEB: Open proposal; review eligibility result
alt Reinsurer approves
  RM -> API: POST /cycles/{id}/approve\n(step_token)
  API -> AUDIT: INSERT REINSURER_APPROVED event
  API -> SF: SendTaskSuccess — step_token
else Reinsurer requests adjustment
  RM -> API: POST /cycles/{id}/adjust\n(adjustment_note)
  API -> AUDIT: INSERT ADJUSTMENT_REQUESTED event
  API -> SF: SendTaskSuccess — step_token (adjusted)
  SF -> SES: Notify counterparty of adjustment
  CP -> API: POST /cycles/{id}/accept-adjustment
  API -> AUDIT: INSERT ADJUSTMENT_ACCEPTED event
  SF -> SES: Re-notify Reconciliation Manager
  RM -> API: POST /cycles/{id}/approve
  API -> AUDIT: INSERT REINSURER_APPROVED event
  API -> SF: SendTaskSuccess — step_token
end

== Phase 4: Counter-Sign and Seal ==

SF -> SES: Send "Please counter-sign cycle {id}"\nto Counterparty Administrator
SES -->> CP: Email — counter-sign request
CP -> WEB: Open portal; review and sign
CP -> API: POST /cycles/{id}/counter-sign
API -> AUDIT: INSERT CYCLE_SIGNED event\n(is_final=true, previous_hash, event_hash)
note over SF: Workflow complete — execution status = SUCCEEDED
API -> AUDIT: INSERT WORKFLOW_COMPLETED event
API -->> WEB: Cycle status = SIGNED ✅

=== Approval Workflow State Machine

.Reconciliation Cycle — State Machine
[plantuml,case03-state-machine,format=svg]
....
@startuml
skinparam backgroundColor #fafafa
skinparam defaultFontName Arial
skinparam state {
  BackgroundColor #E3F2FD

  ArrowColor #1565C0

[*] --> FILE_PENDING : Cycle opened

FILE_PENDING --> FILE_UPLOADED : Counterparty uploads data file\n[SHA-256 checksum verified]
FILE_UPLOADED --> ELIGIBILITY_RUNNING : Step Functions invokes\nEligibility Engine
ELIGIBILITY_RUNNING --> PROPOSAL_READY : Calculation complete
PROPOSAL_READY --> REINSURER_REVIEW : Notification sent to\nReconciliation Manager

REINSURER_REVIEW --> REINSURER_APPROVED : Manager approves proposal

=== Audit Ledger Design

The audit ledger is the platform's trust anchor. It is a separate append-only schema (`audit`) within the same PostgreSQL RDS instance, with distinct privileges:

* The application role has `INSERT` only — no `UPDATE`, no `DELETE`
* A dedicated verification role has `SELECT` only
* Database superusers are restricted by IAM policy; access requires a break-glass procedure logged in CloudTrail

[source,sql]
----
-- Audit events table (append-only; no updates or deletes permitted)
CREATE TABLE audit.events (
    id              BIGSERIAL       PRIMARY KEY,
    tenant_id       UUID            NOT NULL,
    cycle_id        UUID,
    event_type      TEXT            NOT NULL,  -- FILE_UPLOADED | ELIGIBILITY_COMPUTED | REINSURER_APPROVED | ADJUSTMENT_REQUESTED | CYCLE_SIGNED | ...
    actor_id        UUID            NOT NULL,
    actor_type      TEXT            NOT NULL,  -- INTERNAL | COUNTERPARTY | SYSTEM
    payload         JSONB           NOT NULL,  -- event-specific data (file checksum, result summary, approval note, etc.)
    previous_hash   TEXT            NOT NULL,  -- SHA-256 of the immediately preceding row (empty string for row 1)
    event_hash      TEXT            NOT NULL,  -- SHA-256(previous_hash || event_type || actor_id || payload::text || created_at::text)
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT now()
);

-- Restrict to INSERT only for the application role
REVOKE ALL ON audit.events FROM app_role;
GRANT INSERT ON audit.events TO app_role;
GRANT SELECT ON audit.events TO verify_role;

-- Row-Level Security ensures tenants cannot read each other's audit records
ALTER TABLE audit.events ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON audit.events
    USING (tenant_id = current_setting('app.current_tenant_id')::uuid);
----

**Tamper detection:** A weekly Lambda job (`audit-verify`) recomputes every row's `event_hash` and checks that each `previous_hash` matches the preceding row's `event_hash`. Any discrepancy triggers an immediate alert to the compliance team via SNS.

== Option 3: Event-Sourced Architecture

=== Overview

[cols="1,2"]
|===
|Timeline |13 months
|CAPEX |~$1.1M (incl. 25% contingency)
|OPEX / month |~$4,500–$5,500
|Team |1 Architect + 4 Developers + 1 Security + 1 Data Engineer + 1 QA
|Counterparty scale |Unlimited
|Audit strength |Maximum — every state transition is a first-class immutable event; historical state is fully reconstructible by replaying the event log
|===

=== Approach

All state transitions are modelled as immutable domain events stored in an append-only event store (PostgreSQL + S3 event archive). The current state of any reconciliation cycle is derived by replaying its event log — there is no mutable state table. Read projections (materialised views or separate read models) serve query traffic.

This provides the strongest possible audit semantics: the event log *is* the audit ledger; tamper detection requires no hash chain because the event store schema is inherently append-only. However, it introduces significant architectural complexity:

* Engineers must think in events, not entities — a different mental model than CRUD
* Queries require projection tables that must be rebuilt if projections change
* Operational tooling for event replay and projection rebuild must be built and maintained
* Debugging requires event log inspection tools

=== When to Choose This Option

Option 3 becomes appropriate when:

* The counterparty portfolio grows beyond 50 and concurrent cycle volume exceeds the Step Functions Standard Workflow throughput limits
* Regulators require full event-log replay capability (not just hash-chain verification)
* The team has existing event sourcing experience and tooling investment is justified

The recommended migration path from Option 2 to Option 3 is to introduce an event bus (Amazon EventBridge) alongside the existing hash-chain ledger, publishing events for new cycles while keeping existing cycles on the hash-chain model — a gradual, non-disruptive evolution.

== Architecture Decisions

=== ADR-001: Immutability — PostgreSQL Hash-Chain Audit Table

*Context:* The platform must provide tamper-evident records that satisfy FCA and Solvency II audit requirements. Options evaluated: blockchain, AWS QLDB, immuDB (Go-based), PostgreSQL with append-only pattern and hash chain, and full event sourcing.

*Decision:* PostgreSQL append-only audit schema with SHA-256 hash chain.

*Rationale:*
* **Blockchain** rejected — the reinsurer is a single custodian; blockchain's distributed consensus overhead solves a problem that does not exist here
* **AWS QLDB** rejected — discontinued by AWS in 2025; long-term viability cannot be assured
* **immuDB** rejected — consistency and transaction management issues emerged in production on a prior reinsurance-adjacent project when integrated from a non-Go application layer (mentor's first-hand experience); migrating away required significant rework
* **Full event sourcing** deferred — architecturally superior but adds significant complexity not justified by the initial counterparty volume
* **PostgreSQL hash chain** chosen — battle-tested operationally; regulators can query it with standard SQL; SHA-256 verification is transparent; PostgreSQL extension ecosystem (pgaudit, temporal tables) adds defence-in-depth without operational risk

=== ADR-002: Multi-Tenancy — Row-Level Security

*Context:* The platform serves multiple independent counterparty insurers who must be strictly isolated from each other. Options: schema-per-tenant, row-level security (RLS), separate databases per tenant.

*Decision:* PostgreSQL Row-Level Security enforced at the database layer; all tenants share a single schema; `app.current_tenant_id` session variable set by the API service on every connection.

*Rationale:* Schema-per-tenant provides the strongest isolation but adds significant migration complexity as counterparty count grows (running schema migrations across 30 schemas is operationally painful). Separate databases per tenant would make cross-tenant admin queries (for the platform operator) impractical. RLS is the pragmatic middle ground — proven in multi-tenant SaaS at this scale, with the additional safety net of WAF rules and API-layer tenant checks.

=== ADR-003: Approval Workflow — AWS Step Functions Standard Workflows

*Context:* The multi-step approval chain (propose → reinsurer review → adjustment rounds → counterparty counter-sign) needs durable state management with human-approval steps that can pause for hours or days.

*Decision:* AWS Step Functions Standard Workflows with wait-for-callback task tokens.

*Rationale:* Step Functions Standard Workflows provide built-in execution history (up to 90 days, queryable via API) — this history is a natural secondary audit artifact alongside the hash-chain ledger. The wait-for-callback pattern allows a workflow to pause for a human action indefinitely (up to 1 year) without polling loops. A custom in-app state machine would require maintaining durable execution state manually and building equivalent history and retry logic from scratch. Step Functions' visual execution graph also simplifies debugging stalled approvals.

=== ADR-004: File Exchange — S3 Pre-Signed URLs with SFTP Fallback

*Context:* Counterparties need to submit monthly data files securely. Options: SFTP-only, web upload via S3 pre-signed URLs, API-based upload, email attachment (current state).

*Decision:* Web portal upload via S3 pre-signed URLs as the primary channel; AWS Transfer Family SFTP as an opt-in secondary channel for counterparties with existing SFTP tooling.

*Rationale:* Most counterparty contacts are non-technical users who interact with a web portal; SFTP-only would require client software and firewall coordination. Pre-signed URLs allow the browser to upload directly to S3 without proxying through the API service (better performance, lower cost, no file size limits from API gateway). SFTP is retained as a fallback to avoid blocking counterparties with legacy automation.

=== ADR-005: Authentication — Cognito with SAML Federation

*Context:* The platform serves two user populations: internal reinsurer staff (who have a corporate identity provider) and external counterparty administrators (who do not have a shared IdP).

*Decision:* AWS Cognito User Pool for external counterparty users (MFA enforced, email-based registration); Cognito + SAML 2.0 identity federation for internal reinsurer users (federated from the corporate IdP).

*Rationale:* A single Cognito deployment covers both populations with different authentication paths. Cognito MFA is mandatory for all users out of the box. SAML federation removes the need to manage internal user credentials separately from the corporate directory. Building a custom auth layer would require significant security investment with no advantage over a managed service.

=== Disaster Recovery

* **Strategy:** Active-passive; primary in eu-west-2 (London); DR in eu-west-1 (Ireland)
* **RDS:** Multi-AZ automatic failover within eu-west-2 (RTO ~1 min for AZ failure); AWS Backup cross-region snapshots to eu-west-1 (RPO = 24h for full region failure)
* **S3:** Cross-Region Replication to eu-west-1 with 15-minute SLA; versioning enabled in both regions
* **Audit Ledger:** PostgreSQL Multi-AZ replication ensures audit events are synchronously replicated (RPO = 0 for AZ failure)
* **RTO target:** < 1 hour for full region failover; documented DR runbook tested quarterly

=== Hypercare (Weeks 1–4 after First Counterparty Go-Live)

* Daily stand-up with reinsurer IT and reconciliation ops team

=== Counterparty Onboarding Runbook

1. Provision tenant (ID, name, country code) in platform admin portal
2. Upload contract definition (rules JSON) and verify parsing
3. Provision counterparty administrator user (Cognito invite email + MFA setup)
4. Run synthetic test cycle: counterparty uploads sample file → validate eligibility output against contract rules
5. UAT sign-off (counterparty + reinsurer compliance lead)
6. First live cycle: run in parallel with Excel for one month
7. Decommission Excel process for this counterparty

=== Audit Ledger Health

* Weekly Lambda job (`audit-verify`) recomputes hash chain for all events in the last 7 days; alerts compliance team on any discrepancy via SNS → email
* Monthly full-chain verification for regulatory assurance
* Quarterly compliance report: cycle count, event count, verification pass rate, any anomalies
