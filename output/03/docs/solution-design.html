1. Glossary

Term Definition

ADR

Architecture Decision Record — a short document capturing a significant architectural choice, the context that prompted it, and the alternatives considered

Audit Ledger

The cycle_events append-only table that records every state transition in the reconciliation cycle aggregate; INSERT-only enforced at the RLS layer; streamed to S3 Glacier via Debezium CDC for the 10-year Solvency II compliance archive

CDC

Change Data Capture — a technique for reading database transaction logs (WAL) to stream row-level changes as events; used here via Debezium to publish cycle_events inserts to S3 Glacier without dual-write in application code

CAPEX

Capital Expenditure — one-time development and infrastructure setup costs

Counterparty

An independent insurance company that holds one or more reinsurance contracts with the client; a fully separate legal entity and external tenant on the platform

Eligibility

The determination of which individuals in a monthly data file fall within the risk coverage of a given contract, triggering a reinsurance compensation obligation

Hash Chain

A sequence of cryptographic hashes where each entry incorporates the hash of its predecessor; superseded in this design by the cycle_events append-only event log with RLS-enforced immutability

Signed Receipt

A KMS-signed JSON document delivered to a counterparty at CycleSealed; contains cycle ID, file SHA-256 hashes, event chain hash, and sealed timestamp; allows the counterparty to independently verify the sealed record without platform access

Longevity Risk

The financial risk borne by an insurer when insured individuals outlive actuarial expectations, requiring continued pension or annuity payments beyond the projected period

MFA

Multi-Factor Authentication — a login requirement for a second verification step (e.g. OTP) beyond a password; required for all platform users

MoSCoW

Prioritisation framework: Must have / Should have / Could have / Won’t have

OPEX

Operational Expenditure — recurring monthly costs for infrastructure, managed services, and licences

Pension Portfolio

A batch of insured individuals covered under a single longevity or pension reinsurance contract, tracked as a unit in the reconciliation process

PRA

Prudential Regulation Authority — UK regulator overseeing insurance and reinsurance firms' capital adequacy

Reconciliation Cycle

The monthly (or periodic) end-to-end process: counterparty submits data file → reinsurer calculates eligibility → both parties negotiate and sign off on compensation

Reinsurance

Insurance sold to insurance companies; when an insurer faces excessive longevity or pension risk, it offloads part of that risk to a reinsurer in exchange for premium payments

RLS

Row-Level Security — a PostgreSQL feature that enforces per-tenant data access at the database layer, preventing one counterparty from accessing another’s records

Solvency II

EU/UK regulatory framework governing insurance and reinsurance capital adequacy; requires auditable, long-term records of all risk transfer transactions

Application State Machine

A workflow state machine implemented within the Approval Workflow module; the workflow_state column on reconciliation_cycles tracks each cycle through defined states; no external orchestration service required at current scale

TCO

Total Cost of Ownership — full cost including development, infrastructure, and ongoing operations over a defined period

Tenant

A single counterparty organisation on the platform; each tenant’s data is strictly isolated from all other tenants

2. Executive Summary

2.1. Context

A UK-based reinsurance firm manages longevity and pension risk contracts with multiple independent insurance company counterparties. Each month, counterparties submit data files listing insured individuals still alive; the reinsurer’s team applies contract rules to determine compensation, then both parties exchange proposals, negotiate adjustments, and sign off — entirely through email and Excel spreadsheets.

This manual process requires a large team of reconciliation managers. Trust between independent entities is established through repeated human verification. The client’s innovation strategy seeks to automate this inter-company reconciliation, replacing manual labour with a verifiable, auditable digital platform — targeting a 2–4× reduction in reconciliation headcount while meeting UK FCA and Solvency II record-keeping obligations.

6.6. Audit Ledger Design

The audit ledger is the platform’s trust anchor. It uses a selective event sourcing model: the reconciliation cycle aggregate is event-sourced; all other entities use conventional relational tables. This is the same architectural boundary drawn by Monzo (account aggregate event-sourced, customer profiles CRUD) and ING Bank (financial transaction aggregate event-sourced, product configuration CRUD) — applying the pattern only where immutability is the primary requirement.

Industry precedent. Monzo and ING Bank independently found that event sourcing 15–20% of the domain (the financial transaction aggregate) delivers 80% of the compliance value. Revolut enforces immutability on financial tables via RLS-blocked mutations — no external event store. Grab Financial uses Debezium CDC over the PostgreSQL WAL to derive an immutable audit archive without dual-write in application code. All three patterns influence the design below.

cycle_events — the append-only source of truth:

Each row records a single state transition scoped to a reconciliation cycle (stream), carrying the event type, a versioned JSONB payload, the actor, and a timestamp. The (stream_id, version) unique constraint provides optimistic concurrency — a duplicate version on the same stream fails with a constraint violation. The application role holds INSERT and SELECT only; RLS policies block UPDATE and DELETE at the database layer, unconditionally.

Twelve event types cover the full cycle lifecycle: FilesRequested, FileSubmitted, FileRejected, FileNormalisationCompleted, EligibilityStarted, EligibilityCompleted, ReviewStarted, AdjustmentProposed, AdjustmentAccepted, AdjustmentRejected, CounterpartySigned, CycleSealed. New event types are additive changes; existing types are versioned via a schema_version field in payload.

Materialized views for current state: Six PostgreSQL materialized views derive portal-facing query state from cycle_events. Each refreshes incrementally on INSERT via trigger. Re-building any view from scratch requires only replaying cycle_events — the table is never modified.

Debezium CDC — compliance archive without dual-write:

Debezium runs as a Fargate sidecar, reads the PostgreSQL WAL, and streams cycle_events inserts to S3 Glacier as Parquet files. The application writes once (INSERT); Debezium handles the archive asynchronously. There is no dual-write failure mode: the application state and the compliance archive cannot diverge because the archive is derived from the WAL, not written independently. S3 Glacier provides the 10-year Solvency II retention at near-zero cost. Compliance investigations query the archive via Athena — the operational database is never used for historical reconstruction.

KMS-signed cycle receipts and counterparty event visibility:

The reinsurer controls the infrastructure, so a receipt only at CycleSealed proves the final state is authentic but leaves the intermediate process opaque. Two mechanisms address this. First, the counterparty portal exposes the full ordered event timeline for their cycles — every event (file submitted, eligibility completed, adjustment proposed, etc.) with actor and timestamp — so the process is transparent without requiring trust in any single party. Second, a KMS-signed receipt (RSA-PSS, cycle ID, file SHA-256 hashes, event chain hash, timestamp) is issued at two checkpoints: EligibilityCompleted and CycleSealed. Holding both receipts, the counterparty can verify that the eligibility result presented for their signature was not altered after calculation — any such change would produce a different event chain hash. The public key is published in the platform’s trust document; receipts are delivered via SES and available for download from the portal.

pgaudit is retained as defence-in-depth, capturing DML statement logs at the database layer independently of the application event log.

6.7. Data Model

The data model spans four domain areas: tenant management (counterparty identity, users, data residency zone), contract configuration (versioned rule definitions and required file types per contract), reconciliation lifecycle (one cycle per contract per period, typed file uploads, eligibility results, approval history, cross-cycle adjustments), and audit (cycle_events — the append-only event log that drives the entire cycle lifecycle). Column-level schema definitions are delivered as Phase 1 migration scripts.

6.10. Eligibility Engine — Rule Schema

Contract rules are stored as structured expression trees (logical combinators, range checks, stepped rate tables) validated against a versioned JSON Schema at upload time. The engine evaluates both eligibility and compensation rules without any contract-specific code — new node types are added once to the evaluator and immediately available to all contracts. All monetary values and rates are represented as decimal strings to prevent IEEE 754 rounding artefacts. The full node type taxonomy and the Phase 1→2 complexity gate (which validates that all representative contract types are expressible before engine build begins) are defined in the Phase 1 Technical Specification.

8.2. Approach

All state transitions are modelled as immutable domain events stored in an append-only event store (PostgreSQL + S3 event archive). The current state of any reconciliation cycle is derived by replaying its event log — there is no mutable state table. Read projections (materialised views or separate read models) serve query traffic.

This provides the strongest possible audit semantics: the event log is the audit ledger; tamper detection requires no hash chain because the event store schema is inherently append-only. However, it introduces significant architectural complexity:

  • Engineers must think in events, not entities — a different mental model than CRUD

  • Queries require projection tables that must be rebuilt if projections change

  • Operational tooling for event replay and projection rebuild must be built and maintained

  • Debugging requires event log inspection tools

8.3. When to Choose This Option

Option 3 becomes appropriate when:

  • The counterparty portfolio grows beyond 50 and the application state machine’s cycle volume or branching complexity justifies extraction to a managed workflow engine

  • Regulators require full event-log replay capability (not just hash-chain verification)

  • The team has existing event sourcing experience and tooling investment is justified

The recommended migration path from Option 2 to Option 3 is to introduce CQRS projections alongside the existing cycle_events log — the event log is already the source of truth, so adding separate read models and an event bus (Amazon EventBridge) is an additive change, not a rewrite. Existing cycle event history migrates naturally since the event log is already append-only.

9.2. Regulatory Compliance Gap Analysis

Regulation Gap in current design Proposed handling

Solvency II Pillar III — Article 259

Article 259 requires a documented audit trail of actuarial computations, including calculation inputs and outputs. The cycle_events log provides tamper evidence via RLS + CDC archive, but does not explicitly define the required granularity of EligibilityCompleted event payload content. Define payload schema with compliance team during Investigation Period.

The ELIGIBILITY_COMPUTED audit event payload must include: input file SHA-256, contract rule version, normalisation_mapping_version, per-individual eligibility flags, and the total compensation amount. The exact schema is to be confirmed with the compliance team in the Phase 1 compliance workshop.

FCA SYSC 9.1

SYSC 9.1 requires records of all client-facing communications. The current design logs file submissions and approval actions but does not explicitly capture negotiation messages (adjustment requests and free-text responses) in the audit ledger.

ADJUSTMENT_REQUESTED and ADJUSTMENT_ACCEPTED events must include the full adjustment note text in their payload. Free-text negotiation messages entered via the portal are appended to the audit ledger as COMMUNICATION_RECORDED events at send time.

GDPR Article 17 — Right to Erasure

The cycle_events log is append-only by design. If counterparty employees' personal data (names, email addresses) are stored inline in event payloads, a Right to Erasure request cannot be fulfilled. Mitigation: store only opaque identifiers (UUIDs) in event payloads; resolve to PII only at query time via the users table, which supports pseudonymisation. Validate approach in DPIA during Investigation Period.

Personal identifiers (user name, email) are stored only in the mutable users table with a reference actor_id UUID. Audit event payloads contain only the UUID, never the raw personal data. On a Right to Erasure request, the user record is anonymised in the users table; the UUID reference in audit events remains intact and the chain is unaffected.

10. Architecture Decisions

10.1. ADR-001: Immutability — Selective Event Sourcing on Cycle Aggregate + CDC Audit Archive

Context: The platform must provide tamper-evident records that satisfy FCA and Solvency II audit requirements. Options evaluated: blockchain, AWS QLDB, immuDB (Go-based), dual-layer audit (S3 Object Lock + PostgreSQL hash-chain), full event sourcing across all aggregates, and selective event sourcing on the reconciliation cycle aggregate only.

Decision: Selective event sourcing applied to the reconciliation cycle aggregate only. A single cycle_events table is the append-only source of truth for cycle lifecycle. All other entities (contracts, counterparties, users) use conventional relational tables. Debezium CDC streams cycle_events inserts to S3 Glacier as the 10-year compliance archive. KMS-signed cycle receipts are issued to counterparties at CycleSealed.

Write semantics: All cycle lifecycle transitions are written as INSERT-only events to cycle_events. RLS policies block UPDATE and DELETE at the database layer — the application role has INSERT and SELECT only; no UPDATE or DELETE privilege exists. Current cycle state is derived from materialized views over cycle_events. Debezium reads the PostgreSQL WAL and streams events to S3 asynchronously — the application does not write to the archive; CDC handles it.

Rationale:

  • Selective event sourcing — applied to the reconciliation cycle aggregate only; contracts, counterparties, and users use CRUD. Monzo and ING Bank arrived at the same boundary independently: event source where immutability is the core requirement, use relational tables everywhere else.

  • PostgreSQL as the event store — no additional infrastructure dependency; RLS provides tenant isolation natively; Debezium over the WAL delivers the immutable archive without dual-write in application code.

  • CDC (Debezium) as the compliance archive — single write path (INSERT into cycle_events); CDC derives the S3 Glacier archive asynchronously. No divergence failure mode.

  • KMS-signed cycle receipts — close the inter-party trust gap at CycleSealed without blockchain; the counterparty can verify the receipt independently without platform access.

  • Blockchain rejected — the reinsurer is the sole custodian; distributed consensus adds overhead with no benefit in a single-custodian model.

  • AWS QLDB rejected — discontinued by AWS. immuDB rejected — production integration issues with consistency and transaction management. Dual-layer audit rejected — dual-write creates a divergence failure mode; two co-primary sources of truth add complexity without adding trust.

  • pgaudit retained as defence-in-depth alongside the application event log.

10.2. ADR-002: Multi-Tenancy — Row-Level Security

Context: The platform serves multiple independent counterparty insurers who must be strictly isolated from each other. Options: schema-per-tenant, row-level security (RLS), separate databases per tenant.

Decision: PostgreSQL Row-Level Security enforced at the database layer; all tenants share a single schema; app.current_tenant_id set via SET LOCAL (transaction-scoped) by the API service at the start of every database transaction.

Rationale: Schema-per-tenant provides the strongest isolation but adds significant migration complexity as counterparty count grows (running schema migrations across 30 schemas is operationally painful). Separate databases per tenant would make cross-tenant admin queries (for the platform operator) impractical. RLS is the pragmatic middle ground — proven in multi-tenant SaaS at this scale, with the additional safety net of WAF rules and API-layer tenant checks.

SET LOCAL is used instead of SET so that the tenant context is transaction-scoped and automatically cleared when the transaction ends. This prevents the known production failure mode where a connection pool reuses a session before the session variable is cleared — which would silently expose the prior tenant’s data to the next request on that connection.

10.3. ADR-003: Approval Workflow — Application-Layer State Machine

Context: The multi-level approval chain (propose → L1 reinsurer review → L2 senior review → adjustment rounds → counterparty counter-proposal or revised file → counter-sign) needs durable state management with human-approval steps that can pause for hours or days. The workflow must support a chain of 2–4+ approvers per cycle and allow the counterparty to re-submit revised data files at any point before seal.

Decision: Application-layer state machine implemented within the Approval Workflow module. The reconciliation_cycles table has a workflow_state column tracking states: AWAITING_FILES → AWAITING_ELIGIBILITY → AWAITING_L1 → AWAITING_L2 → AWAITING_COUNTERPARTY → COMPLETED / DISPUTED / ELIGIBILITY_FAILED. A background job runner (running inside the ECS Fargate service) handles the 72-hour escalation timer. Other modules call ApprovalWorkflow.transition(cycleId, event) — a clean interface that allows extraction to Step Functions later if the workflow grows beyond ~5 concurrent workflow types or multi-week execution lifetimes.

Rationale: Step Functions rejected — designed to orchestrate Lambda functions across service boundaries; those boundaries don’t exist in a monolith, and IAM/task-token complexity is unwarranted at 180–240 workflows/year. Durable state is already in the reconciliation_cycles row; no external engine is needed to persist between human actions. The ApprovalWorkflow.transition(cycleId, event) interface makes future extraction additive.

10.4. ADR-004: Authentication — Cognito User Pools with MFA; SAML Deferred

Context: The platform serves two user populations: internal reinsurer staff (who may have a corporate identity provider) and external counterparty administrators (who do not have a shared IdP).

Decision: Cognito User Pools with email + MFA for Phase 1. SAML 2.0 federation is available as a Phase 2 addition when a specific counterparty IT team requires enterprise IdP integration. The Cognito User Pool is configured with an IdP placeholder to make this addition a configuration change, not a code change. Both paths issue JWTs from one issuer; a custom:user_type claim (INTERNAL or COUNTERPARTY) drives RBAC in the API service.

Rationale: SAML federation setup requires metadata exchange with the corporate IT team, which is a coordination dependency the platform build should not block on. Cognito User Pools with MFA is sufficient for all Phase 1 users — internal staff included. The IdP placeholder means the federation is a one-day configuration task whenever a specific counterparty requires it. Cognito MFA is enforced for all users regardless of the authentication path.

10.5. ADR-005: Compute — ECS Fargate Modular Monolith + RDS PostgreSQL

Context: The workload is monthly peaks with near-zero baseline between reconciliation cycles (a few portal logins per week). The architecture is a modular monolith. Options: ECS Fargate (container tasks behind ALB), Lambda + API Gateway (pay-per-invocation), EKS (Kubernetes).

Decision: Single ECS Fargate service hosting the entire modular monolith (API + eligibility engine + background jobs + Debezium CDC sidecar), fronted by an Application Load Balancer. RDS PostgreSQL (db.t4g.medium, Multi-AZ) for the database.

Rationale: Lambda rejected — function-level granularity doesn’t exist in a monolith; Fargate gives deterministic connection pooling and no execution-time ceiling. EKS rejected — operational overhead not justified for a 6-person team. Aurora Serverless v2 rejected — monthly burst is the worst fit for serverless cold-start scaling; provisioned db.t4g.medium delivers predictable latency at peak.

10.6. ADR-006: Contract Rules — Structured Expression Tree

Context: The platform must accept contract definitions as structured metadata without constraining contract authors to a rigid schema that breaks when a new contract type is introduced. Options: flat JSON with code-per-contract, expression tree with generic evaluator, embedded DSL (e.g. SpEL/MVEL), Rete-based rule engine.

Decision: Contract rules stored as a structured expression tree evaluated by a generic engine. Validated against a versioned JSON Schema at upload time. See the Eligibility Engine — Rule Schema section for the node type taxonomy and decimal precision approach.

Rationale:

  • Flat JSON rejected — breaks when a contract has stepped rates by age band, multi-condition eligibility, or annuity factor tables. Every new contract type would require a code change.

  • Expression tree chosen — the engine evaluates eligibility and compensation rules as tree structures without contract-specific code. New node types are added once to the evaluator, then usable across all contracts. A schema_version field ensures reproducibility.

  • Embedded DSL (SpEL/MVEL) rejected — creates a security risk (arbitrary code execution) and makes audit reproducibility harder.

  • Rete-based rule engine (Drools) rejected — operational overhead not justified at this scale.

11.3. Security Controls

Control Approach

Authentication

Single Cognito User Pool; Cognito-native (email/password + MFA) for Phase 1 all users; SAML 2.0 federation available as Phase 2 addition via pre-configured IdP placeholder; MFA enforced for all users

Authorisation

Role-based access control (RBAC) with five roles spanning reinsurer, counterparty, compliance, and platform administration. Every approval action (L1 approve, L2 approve, counter-proposal, final sign-off) enforces three checks in the application layer: (1) re-validate the caller’s Cognito JWT, (2) confirm the approver’s role matches the required approval level for this action, (3) confirm the target cycle belongs to the caller’s tenant. Authentication alone (valid JWT) is not sufficient — all three checks must pass before any state transition is executed.

Data isolation

PostgreSQL RLS at DB layer; transaction-scoped tenant context to prevent connection-pool bleed; WAF rate limiting attached to ALB

Encryption

AES-256 at rest (KMS-managed); TLS 1.2+ in transit; dedicated KMS CMK for audit-critical data; S3 audit bucket uses SSE-KMS with the audit CMK

Network security

ECS Fargate tasks in private subnets; Aurora not publicly accessible; WAF (ALB-attached) with OWASP managed rule group

S3 audit bucket controls

Bucket policy includes explicit Deny on s3:DeleteObject and s3:PutObject without Object Lock headers — prevents any principal (including account root) from bypassing Object Lock. S3 raw file bucket uses Object Lock Governance Mode (allows operator override with justification; enables non-repudiation if a counterparty disputes that the system altered their file).

Audit logging

Three layers: AWS CloudTrail (API calls), database statement logging, application-level audit ledger (business events)

Break-glass access

Superuser access requires documented procedure with alerting; all access logged

11.4. Disaster Recovery

Primary region is eu-west-2 (London). RDS Multi-AZ provides automatic AZ failover (RTO ~1 min, RPO = 0). Daily cross-region snapshots to eu-west-1 via AWS Backup and S3 Cross-Region Replication provide full-region DR (RPO = 24h, RTO < 4 hours). No active standby is maintained in eu-west-1 — the same Terraform module provisions a recovery stack on demand. Maintenance windows are scheduled outside month-end submission periods.
