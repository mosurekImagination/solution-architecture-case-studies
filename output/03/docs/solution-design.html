1. Glossary

Term Definition

ADR

Architecture Decision Record — a short document capturing a significant architectural choice, the context that prompted it, and the alternatives considered

Audit Ledger

An append-only, tamper-evident log of every state transition within the platform; the digital equivalent of the paper trail currently maintained through email exchanges

CAPEX

Capital Expenditure — one-time development and infrastructure setup costs

Counterparty

An independent insurance company that holds one or more reinsurance contracts with the client; a fully separate legal entity and external tenant on the platform

Eligibility

The determination of which individuals in a monthly data file fall within the risk coverage of a given contract, triggering a reinsurance compensation obligation

Hash Chain

A sequence of SHA-256 hashes where each entry incorporates the hash of the previous entry; any tampering with a historical record breaks the chain and is immediately detectable

Longevity Risk

The financial risk borne by an insurer when insured individuals outlive actuarial expectations, requiring continued pension or annuity payments beyond the projected period

MFA

Multi-Factor Authentication — a login requirement for a second verification step (e.g. OTP) beyond a password; required for all platform users

MoSCoW

Prioritisation framework: Must have / Should have / Could have / Won’t have

OPEX

Operational Expenditure — recurring monthly costs for infrastructure, managed services, and licences

Pension Portfolio

A batch of insured individuals covered under a single longevity or pension reinsurance contract, tracked as a unit in the reconciliation process

PRA

Prudential Regulation Authority — UK regulator overseeing insurance and reinsurance firms' capital adequacy

Reconciliation Cycle

The monthly (or periodic) end-to-end process: counterparty submits data file → reinsurer calculates eligibility → both parties negotiate and sign off on compensation

Reinsurance

Insurance sold to insurance companies; when an insurer faces excessive longevity or pension risk, it offloads part of that risk to a reinsurer in exchange for premium payments

RLS

Row-Level Security — a PostgreSQL feature that enforces per-tenant data access at the database layer, preventing one counterparty from accessing another’s records

Solvency II

EU/UK regulatory framework governing insurance and reinsurance capital adequacy; requires auditable, long-term records of all risk transfer transactions

Step Functions

AWS Step Functions — a managed workflow orchestration service; used here to implement the approval state machine with built-in execution history and human-approval callbacks

TCO

Total Cost of Ownership — full cost including development, infrastructure, and ongoing operations over a defined period

Tenant

A single counterparty organisation on the platform; each tenant’s data is strictly isolated from all other tenants

2. Executive Summary

2.1. Context

A UK-based reinsurance firm manages longevity and pension risk contracts with multiple independent insurance company counterparties. Each month, counterparties submit data files listing insured individuals still alive; the reinsurer’s team applies contract rules to determine compensation, then both parties exchange proposals, negotiate adjustments, and sign off — entirely through email and Excel spreadsheets.

This manual process requires a large team of reconciliation managers. Trust between independent entities is established through repeated human verification. The client’s innovation strategy seeks to automate this inter-company reconciliation, replacing manual labour with a verifiable, auditable digital platform — targeting a 2–4× reduction in reconciliation headcount while meeting UK FCA and Solvency II record-keeping obligations.

6.6. Audit Ledger Design

The audit ledger is the platform’s trust anchor. It is a separate append-only schema (audit) within the same PostgreSQL RDS instance, with distinct privileges:

  • The application role has INSERT only — no UPDATE, no DELETE

  • A dedicated verification role has SELECT only

  • Database superusers are restricted by IAM policy; access requires a break-glass procedure logged in CloudTrail

-- Audit events table (append-only; no updates or deletes permitted)
CREATE TABLE audit.events (
    id              BIGSERIAL       PRIMARY KEY,
    tenant_id       UUID            NOT NULL,
    cycle_id        UUID,
    event_type      TEXT            NOT NULL,  -- FILE_UPLOADED | ELIGIBILITY_COMPUTED | REINSURER_APPROVED | ADJUSTMENT_REQUESTED | CYCLE_SIGNED | ...
    actor_id        UUID            NOT NULL,
    actor_type      TEXT            NOT NULL,  -- INTERNAL | COUNTERPARTY | SYSTEM
    payload         JSONB           NOT NULL,  -- event-specific data (file checksum, result summary, approval note, etc.)
    previous_hash   TEXT            NOT NULL,  -- SHA-256 of the immediately preceding row (empty string for row 1)
    event_hash      TEXT            NOT NULL,  -- SHA-256(previous_hash || event_type || actor_id || payload::text || created_at::text)
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT now()
);

-- Restrict to INSERT only for the application role
REVOKE ALL ON audit.events FROM app_role;
GRANT INSERT ON audit.events TO app_role;
GRANT SELECT ON audit.events TO verify_role;

-- Row-Level Security ensures tenants cannot read each other's audit records
ALTER TABLE audit.events ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON audit.events
    USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

Tamper detection: A weekly Lambda job (audit-verify) recomputes every row’s event_hash and checks that each previous_hash matches the preceding row’s event_hash. Any discrepancy triggers an immediate alert to the compliance team via SNS.

6.10. Testing Approach

  • Eligibility engine unit tests: Every contract rule has a corresponding test vector (input record → expected eligibility flag); side-by-side validation against existing Excel output used during Phase 1 workshops

  • RLS penetration tests: Automated suite that attempts cross-tenant data access via API and direct DB connection; runs on every deployment

  • Hash-chain integrity tests: Test suite that inserts events, tampers with one, and verifies the verification Lambda detects the break

  • Month-end load test: Concurrent file submission simulation (20 counterparties) run against staging before each Phase go-live

  • Counterparty UAT: First counterparty completes a full test cycle with synthetic data before live cycle approval

8.2. Approach

All state transitions are modelled as immutable domain events stored in an append-only event store (PostgreSQL + S3 event archive). The current state of any reconciliation cycle is derived by replaying its event log — there is no mutable state table. Read projections (materialised views or separate read models) serve query traffic.

This provides the strongest possible audit semantics: the event log is the audit ledger; tamper detection requires no hash chain because the event store schema is inherently append-only. However, it introduces significant architectural complexity:

  • Engineers must think in events, not entities — a different mental model than CRUD

  • Queries require projection tables that must be rebuilt if projections change

  • Operational tooling for event replay and projection rebuild must be built and maintained

  • Debugging requires event log inspection tools

8.3. When to Choose This Option

Option 3 becomes appropriate when:

  • The counterparty portfolio grows beyond 50 and concurrent cycle volume exceeds the Step Functions Standard Workflow throughput limits

  • Regulators require full event-log replay capability (not just hash-chain verification)

  • The team has existing event sourcing experience and tooling investment is justified

The recommended migration path from Option 2 to Option 3 is to introduce an event bus (Amazon EventBridge) alongside the existing hash-chain ledger, publishing events for new cycles while keeping existing cycles on the hash-chain model — a gradual, non-disruptive evolution.

10. Architecture Decisions

10.1. ADR-001: Immutability — PostgreSQL Hash-Chain Audit Table

Context: The platform must provide tamper-evident records that satisfy FCA and Solvency II audit requirements. Options evaluated: blockchain, AWS QLDB, immuDB (Go-based), PostgreSQL with append-only pattern and hash chain, and full event sourcing.

Decision: PostgreSQL append-only audit schema with SHA-256 hash chain.

Rationale: * Blockchain rejected — the reinsurer is a single custodian; blockchain’s distributed consensus overhead solves a problem that does not exist here * AWS QLDB rejected — discontinued by AWS in 2025; long-term viability cannot be assured * immuDB rejected — consistency and transaction management issues emerged in production on a prior reinsurance-adjacent project when integrated from a non-Go application layer (mentor’s first-hand experience); migrating away required significant rework * Full event sourcing deferred — architecturally superior but adds significant complexity not justified by the initial counterparty volume * PostgreSQL hash chain chosen — battle-tested operationally; regulators can query it with standard SQL; SHA-256 verification is transparent; PostgreSQL extension ecosystem (pgaudit, temporal tables) adds defence-in-depth without operational risk

10.2. ADR-002: Multi-Tenancy — Row-Level Security

Context: The platform serves multiple independent counterparty insurers who must be strictly isolated from each other. Options: schema-per-tenant, row-level security (RLS), separate databases per tenant.

Decision: PostgreSQL Row-Level Security enforced at the database layer; all tenants share a single schema; app.current_tenant_id session variable set by the API service on every connection.

Rationale: Schema-per-tenant provides the strongest isolation but adds significant migration complexity as counterparty count grows (running schema migrations across 30 schemas is operationally painful). Separate databases per tenant would make cross-tenant admin queries (for the platform operator) impractical. RLS is the pragmatic middle ground — proven in multi-tenant SaaS at this scale, with the additional safety net of WAF rules and API-layer tenant checks.

10.3. ADR-003: Approval Workflow — AWS Step Functions Standard Workflows

Context: The multi-step approval chain (propose → reinsurer review → adjustment rounds → counterparty counter-sign) needs durable state management with human-approval steps that can pause for hours or days.

Decision: AWS Step Functions Standard Workflows with wait-for-callback task tokens.

Rationale: Step Functions Standard Workflows provide built-in execution history (up to 90 days, queryable via API) — this history is a natural secondary audit artifact alongside the hash-chain ledger. The wait-for-callback pattern allows a workflow to pause for a human action indefinitely (up to 1 year) without polling loops. A custom in-app state machine would require maintaining durable execution state manually and building equivalent history and retry logic from scratch. Step Functions' visual execution graph also simplifies debugging stalled approvals.

10.4. ADR-004: File Exchange — S3 Pre-Signed URLs with SFTP Fallback

Context: Counterparties need to submit monthly data files securely. Options: SFTP-only, web upload via S3 pre-signed URLs, API-based upload, email attachment (current state).

Decision: Web portal upload via S3 pre-signed URLs as the primary channel; AWS Transfer Family SFTP as an opt-in secondary channel for counterparties with existing SFTP tooling.

Rationale: Most counterparty contacts are non-technical users who interact with a web portal; SFTP-only would require client software and firewall coordination. Pre-signed URLs allow the browser to upload directly to S3 without proxying through the API service (better performance, lower cost, no file size limits from API gateway). SFTP is retained as a fallback to avoid blocking counterparties with legacy automation.

10.5. ADR-005: Authentication — Cognito with SAML Federation

Context: The platform serves two user populations: internal reinsurer staff (who have a corporate identity provider) and external counterparty administrators (who do not have a shared IdP).

Decision: AWS Cognito User Pool for external counterparty users (MFA enforced, email-based registration); Cognito + SAML 2.0 identity federation for internal reinsurer users (federated from the corporate IdP).

Rationale: A single Cognito deployment covers both populations with different authentication paths. Cognito MFA is mandatory for all users out of the box. SAML federation removes the need to manage internal user credentials separately from the corporate directory. Building a custom auth layer would require significant security investment with no advantage over a managed service.

11.4. Disaster Recovery

  • Strategy: Active-passive; primary in eu-west-2 (London); DR in eu-west-1 (Ireland)

  • RDS: Multi-AZ automatic failover within eu-west-2 (RTO ~1 min for AZ failure); AWS Backup cross-region snapshots to eu-west-1 (RPO = 24h for full region failure)

  • S3: Cross-Region Replication to eu-west-1 with 15-minute SLA; versioning enabled in both regions

  • Audit Ledger: PostgreSQL Multi-AZ replication ensures audit events are synchronously replicated (RPO = 0 for AZ failure)

  • RTO target: < 1 hour for full region failover; documented DR runbook tested quarterly
