1. Glossary

Term Definition

ADR

Architecture Decision Record — a short document capturing a significant architectural choice, the context that prompted it, and the alternatives considered

Audit Ledger

An append-only, tamper-evident log of every state transition within the platform; the digital equivalent of the paper trail currently maintained through email exchanges

CAPEX

Capital Expenditure — one-time development and infrastructure setup costs

Counterparty

An independent insurance company that holds one or more reinsurance contracts with the client; a fully separate legal entity and external tenant on the platform

Eligibility

The determination of which individuals in a monthly data file fall within the risk coverage of a given contract, triggering a reinsurance compensation obligation

Hash Chain

A sequence of SHA-256 hashes where each entry incorporates the hash of the previous entry; any tampering with a historical record breaks the chain and is immediately detectable

Longevity Risk

The financial risk borne by an insurer when insured individuals outlive actuarial expectations, requiring continued pension or annuity payments beyond the projected period

MFA

Multi-Factor Authentication — a login requirement for a second verification step (e.g. OTP) beyond a password; required for all platform users

MoSCoW

Prioritisation framework: Must have / Should have / Could have / Won’t have

OPEX

Operational Expenditure — recurring monthly costs for infrastructure, managed services, and licences

Pension Portfolio

A batch of insured individuals covered under a single longevity or pension reinsurance contract, tracked as a unit in the reconciliation process

PRA

Prudential Regulation Authority — UK regulator overseeing insurance and reinsurance firms' capital adequacy

Reconciliation Cycle

The monthly (or periodic) end-to-end process: counterparty submits data file → reinsurer calculates eligibility → both parties negotiate and sign off on compensation

Reinsurance

Insurance sold to insurance companies; when an insurer faces excessive longevity or pension risk, it offloads part of that risk to a reinsurer in exchange for premium payments

RLS

Row-Level Security — a PostgreSQL feature that enforces per-tenant data access at the database layer, preventing one counterparty from accessing another’s records

Solvency II

EU/UK regulatory framework governing insurance and reinsurance capital adequacy; requires auditable, long-term records of all risk transfer transactions

Step Functions

AWS Step Functions — a managed workflow orchestration service; used here to implement the approval state machine with built-in execution history and human-approval callbacks

TCO

Total Cost of Ownership — full cost including development, infrastructure, and ongoing operations over a defined period

Tenant

A single counterparty organisation on the platform; each tenant’s data is strictly isolated from all other tenants

2. Executive Summary

2.1. Context

A UK-based reinsurance firm manages longevity and pension risk contracts with multiple independent insurance company counterparties. Each month, counterparties submit data files listing insured individuals still alive; the reinsurer’s team applies contract rules to determine compensation, then both parties exchange proposals, negotiate adjustments, and sign off — entirely through email and Excel spreadsheets.

This manual process requires a large team of reconciliation managers. Trust between independent entities is established through repeated human verification. The client’s innovation strategy seeks to automate this inter-company reconciliation, replacing manual labour with a verifiable, auditable digital platform — targeting a 2–4× reduction in reconciliation headcount while meeting UK FCA and Solvency II record-keeping obligations.

6.6. Audit Ledger Design

The audit ledger is the platform’s trust anchor. It is a separate append-only schema (audit) within the same Aurora Serverless v2 instance, with distinct privileges:

  • The application role has INSERT only — no UPDATE, no DELETE

  • A dedicated verification role has SELECT only

  • Database superusers are restricted by IAM policy; access requires a break-glass procedure logged in CloudTrail

Each event row stores the event type, acting user, a JSONB payload with event-specific data, and two hash fields (previous_hash, event_hash) that form the per-tenant chain. Row-Level Security isolates tenants at the database layer. The full schema definition — including privilege grants, RLS policies, and hash-chain linking logic — is delivered as part of the Phase 1 database migration scripts.

Per-tenant hash chain: Each tenant has an independent chain. Row N’s previous_hash references the hash of the preceding event for the same tenant_id, not the globally preceding row. This allows concurrent month-end submissions from all counterparties without serialization contention.

KMS-signed genesis: When a tenant is provisioned, a genesis audit event (TENANT_PROVISIONED) is written whose previous_hash is a signature produced by AWS KMS (using a CMK dedicated to audit integrity). This anchors the chain cryptographically — an attacker who deletes and re-inserts all rows cannot forge the genesis signature without access to the KMS key, which is controlled by IAM policy and logged in CloudTrail.

Tamper detection: A Lambda job (audit-verify) recomputes each row’s event_hash and checks that each previous_hash matches the preceding row’s hash for that tenant. The job runs on every read of a sealed cycle (zero-cost at monthly reconciliation volume) and also on a weekly full-chain sweep. Any discrepancy triggers an immediate alert to the compliance team via SNS.

6.7. Data Model

The platform’s core data model comprises ten entities spanning tenant management, contract configuration, reconciliation lifecycle, and audit. Column-level schema definitions are delivered as Phase 1 migration scripts.

Key design points:

  • tenants — each counterparty is a tenant with a designated data residency zone; Row-Level Security isolates all downstream data

  • contracts — versioned contract definitions with expression tree rules stored as JSONB; contract_file_types defines which file types each contract requires

  • reconciliation_cycles — one cycle per contract per period; locks a contract_version at opening time (ADR-009); tracks workflow status

  • cycle_files — typed file uploads (people table, money movement, etc.) with SHA-256 checksums; drives the cycle readiness check

  • eligibility_results — engine output with a generated compensation_amount column derived from the result JSONB; records engine version for reproducibility

  • approval_steps — ordered sequence of L1/L2 approvals, adjustments, and counter-proposals within a cycle

  • adjustments — cross-cycle correction chain tracked via prior_cycle_id, root_cycle_id, and generation (ADR-008)

  • audit.events — append-only ledger with per-tenant SHA-256 hash chain; KMS-signed genesis anchor; no UPDATE or DELETE permitted

6.10. Eligibility Engine — Rule Schema

Contract rules are stored as structured expression trees validated against a versioned JSON Schema. The eligibility engine evaluates eligibility_rule as a boolean expression tree and compensation_rule as a computation tree — both without any contract-specific code. New field types (mortality rate lookup, annuity factor table) are added once to the evaluator, then usable across all contracts without per-contract changes. Each rule set contains a schema_version field so the engine knows which interpreter to use; unknown node types are rejected at contract upload time.

Expression tree node types (initial set):

  • AND / OR — logical combinators; evaluate child conditions

  • NOT — logical negation of a single child condition

  • range — field value within [min, max]; supports open-ended ranges

  • in — field value in a set of allowed values

  • eq — exact match on a single value

  • tiered — stepped rate table; selects rate based on the first matching tier

  • flat — fixed rate per individual (simplest case)

New node types (e.g. lookup for mortality tables, formula for actuarial calculations) are added to the evaluator once and immediately usable in any contract definition without deployment changes.

Complexity ceiling gate: If the Investigation Period finds that more than 20% of contract types require node types not in the initial set (e.g. mortality table lookups, actuarial factor calculations, multi-dimensional tiered rates), the expression tree approach is escalated to a constrained formula DSL before Phase 2 begins. The escalation decision is a Phase 1→2 gate item — it is not deferred.

Decimal precision: All monetary values, rates, and factors in contract rule JSON are represented as strings, not JSON numbers, to prevent IEEE 754 rounding artefacts. The JSON Schema enforces a decimal string pattern; the eligibility engine parses strings into language-native exact decimal types at evaluation time.

Validation and regression: The engine validates rule JSON against a versioned JSON Schema at upload time. During Phase 1, the engine is run against 12 months of historical Excel output for 2–3 representative contracts. A pass requires 100% agreement on eligibility flags and compensation amounts before production use.

6.11. Testing Approach

  • Expression tree evaluator unit tests: Every node type (AND, OR, range, tiered, flat, etc.) has a dedicated test suite; every contract rule has a corresponding test vector (input record → expected eligibility flag); side-by-side validation against existing Excel output used during Phase 1 workshops

  • Decimal precision tests: Verify compensation calculations produce exact decimal results matching Excel output to the penny; no IEEE 754 rounding artefacts

  • Eligibility regression tests: Engine output compared to 12 months of historical Excel results for 2–3 representative counterparties before Phase 2 go-ahead (Phase 1→2 gate)

  • Multi-file ingestion tests: Verify cycle readiness logic — eligibility engine only triggers when all required file types are present; partial submissions do not trigger premature calculations

  • Multi-level approval tests: Full cycle with L1 and L2 approvers; counter-proposal and revised file submission flows; verify all transitions produce correct audit events

  • RLS penetration tests: Automated suite that attempts cross-tenant data access via API and direct DB connection; runs on every deployment

  • Hash-chain integrity tests: Test suite that inserts events, tampers with one, and verifies the verification Lambda detects the break per tenant

  • Lambda deployment tests: Verify all API endpoints respond correctly when deployed to Lambda; cold start latency within acceptable limits for portal interactions

  • Month-end load test: Concurrent file submission simulation (20 counterparties, multiple file types each) run against staging before each Phase go-live

  • Counterparty UAT: First counterparty completes a full test cycle with synthetic data before live cycle approval

8.2. Approach

All state transitions are modelled as immutable domain events stored in an append-only event store (PostgreSQL + S3 event archive). The current state of any reconciliation cycle is derived by replaying its event log — there is no mutable state table. Read projections (materialised views or separate read models) serve query traffic.

This provides the strongest possible audit semantics: the event log is the audit ledger; tamper detection requires no hash chain because the event store schema is inherently append-only. However, it introduces significant architectural complexity:

  • Engineers must think in events, not entities — a different mental model than CRUD

  • Queries require projection tables that must be rebuilt if projections change

  • Operational tooling for event replay and projection rebuild must be built and maintained

  • Debugging requires event log inspection tools

8.3. When to Choose This Option

Option 3 becomes appropriate when:

  • The counterparty portfolio grows beyond 50 and concurrent cycle volume exceeds the Step Functions Standard Workflow throughput limits

  • Regulators require full event-log replay capability (not just hash-chain verification)

  • The team has existing event sourcing experience and tooling investment is justified

The recommended migration path from Option 2 to Option 3 is to introduce an event bus (Amazon EventBridge) alongside the existing hash-chain ledger, publishing events for new cycles while keeping existing cycles on the hash-chain model — a gradual, non-disruptive evolution.

9.2. Regulatory Compliance Gap Analysis

Regulation Gap in current design Proposed handling

Solvency II Pillar III — Article 259

Article 259 requires a documented audit trail of actuarial computations, including calculation inputs and outputs. The hash-chain ledger provides tamper evidence but does not explicitly define the granularity of ELIGIBILITY_COMPUTED payload content.

The ELIGIBILITY_COMPUTED audit event payload must include: input file SHA-256, contract rule version, per-individual eligibility flags, and the total compensation amount. The exact schema is to be confirmed with the compliance team in the Phase 1 compliance workshop.

FCA SYSC 9.1

SYSC 9.1 requires records of all client-facing communications. The current design logs file submissions and approval actions but does not explicitly capture negotiation messages (adjustment requests and free-text responses) in the audit ledger.

ADJUSTMENT_REQUESTED and ADJUSTMENT_ACCEPTED events must include the full adjustment note text in their payload. Free-text negotiation messages entered via the portal are appended to the audit ledger as COMMUNICATION_RECORDED events at send time.

GDPR Article 17 — Right to Erasure

The append-only audit ledger cannot delete records. If counterparty employees' personal data (names, email addresses) are stored inline in audit event payloads, a Right to Erasure request cannot be fulfilled without breaking the hash chain.

Personal identifiers (user name, email) are stored only in the mutable users table with a reference actor_id UUID. Audit event payloads contain only the UUID, never the raw personal data. On a Right to Erasure request, the user record is anonymised in the users table; the UUID reference in audit events remains intact and the chain is unaffected.

10. Architecture Decisions

10.1. ADR-001: Immutability — PostgreSQL Hash-Chain Audit Table

Context: The platform must provide tamper-evident records that satisfy FCA and Solvency II audit requirements. Options evaluated: blockchain, AWS QLDB, immuDB (Go-based), PostgreSQL with append-only pattern and hash chain, and full event sourcing.

Decision: PostgreSQL append-only audit schema with SHA-256 hash chain.

Rationale: * Blockchain rejected — the reinsurer is the sole custodian of this platform; blockchain’s value is distributed consensus between mutually distrusting parties. A single custodian gains nothing from consensus overhead and inherits all of the governance and key-management complexity. * AWS QLDB rejected — discontinued by AWS in 2025; long-term viability cannot be assured. The underlying cryptographic model (hash chain over a Merkle tree) is sound, but the same model can be implemented directly in PostgreSQL without vendor lock-in. * immuDB rejected — despite sound architecture, consistency and transaction management issues emerged in a prior production project integrating from a non-Go application layer; migrating away required significant rework. The risk of opaque internals in a trust-critical system is not acceptable. * Full event sourcing deferred — architecturally superior for auditability but adds projection rebuild complexity and requires specialist knowledge the initial team does not have. Deferred to Option 3 migration when counterparty volume justifies it. * PostgreSQL hash chain chosen — regulators can query it with standard SQL; SHA-256 verification is transparent and reproducible by any auditor; the team already operates PostgreSQL; pgaudit adds DB-level statement logging as defence-in-depth. The chain is partitioned per tenant to eliminate write serialization at month-end; a KMS-signed genesis anchor prevents undetected chain reconstruction.

10.2. ADR-002: Multi-Tenancy — Row-Level Security

Context: The platform serves multiple independent counterparty insurers who must be strictly isolated from each other. Options: schema-per-tenant, row-level security (RLS), separate databases per tenant.

Decision: PostgreSQL Row-Level Security enforced at the database layer; all tenants share a single schema; app.current_tenant_id set via SET LOCAL (transaction-scoped) by the API service at the start of every database transaction.

Rationale: Schema-per-tenant provides the strongest isolation but adds significant migration complexity as counterparty count grows (running schema migrations across 30 schemas is operationally painful). Separate databases per tenant would make cross-tenant admin queries (for the platform operator) impractical. RLS is the pragmatic middle ground — proven in multi-tenant SaaS at this scale, with the additional safety net of WAF rules and API-layer tenant checks.

SET LOCAL is used instead of SET so that the tenant context is transaction-scoped and automatically cleared when the transaction ends. This prevents the known production failure mode where a connection pool reuses a session before the session variable is cleared — which would silently expose the prior tenant’s data to the next request on that connection.

10.3. ADR-003: Approval Workflow — AWS Step Functions Standard Workflows

Context: The multi-level approval chain (propose → L1 reinsurer review → L2 senior review → adjustment rounds → counterparty counter-proposal or revised file → counter-sign) needs durable state management with human-approval steps that can pause for hours or days. The workflow must support a chain of 2–4+ approvers per cycle and allow the counterparty to re-submit revised data files at any point before seal.

Decision: AWS Step Functions Standard Workflows with wait-for-callback task tokens. Each approval level (L1, L2) is implemented as a sub-workflow so the number of levels is configurable per contract tier without changing the Step Functions definition.

Rationale: The wait-for-callback pattern allows a workflow to pause for a human action indefinitely (up to 1 year) without polling loops. A custom in-app state machine would require maintaining durable execution state manually and building equivalent history and retry logic from scratch. Sub-workflows for approval levels allow a new tier to be added per contract without modifying the parent workflow.

Step Functions is the workflow engine; the hash-chain audit ledger is the sole compliance archive. Step Functions execution history is an operational debugging aid only — it is not a regulatory record. Workflow executions are guarded by an idempotency key to prevent duplicate audit events for the same reconciliation cycle.

10.4. ADR-004: File Exchange — S3 Pre-Signed URLs with Typed Multi-File Ingestion

Context: Counterparties need to submit monthly data files securely. The requirements describe five distinct file types per reconciliation cycle (people tables, money movement tables, special condition tables, adjustment records, contract exceptions). Options: SFTP-only, web upload via S3 pre-signed URLs, API-based upload, email attachment (current state).

Decision: Web portal upload via S3 pre-signed URLs as the primary channel; AWS Transfer Family SFTP as an opt-in secondary channel. Each upload is tagged with a file type; the eligibility engine is triggered only when all required file types for a contract have been submitted (tracked via cycle_readiness view).

Rationale: Most counterparty contacts are non-technical users who interact with a web portal; SFTP-only would require client software and firewall coordination. Pre-signed URLs allow the browser to upload directly to S3 without proxying through the API service (better performance, lower cost, no file size limits from API gateway). SFTP is retained as a fallback to avoid blocking counterparties with legacy automation. The typed ingestion model matches real-world practice where counterparties submit different file types at different times during the month — a generic single-file upload would either trigger incomplete calculations or force counterparties to bundle all file types into one upload.

10.5. ADR-005: Authentication — Cognito with SAML Federation

Context: The platform serves two user populations: internal reinsurer staff (who have a corporate identity provider) and external counterparty administrators (who do not have a shared IdP).

Decision: A single AWS Cognito User Pool with two identity providers: Cognito-native (email/password + MFA) for external counterparty users, and SAML 2.0 federation from the corporate IdP for internal reinsurer users. Both paths issue JWTs from one issuer; a custom:user_type claim (INTERNAL or COUNTERPARTY) drives RBAC in the API service.

Rationale: Two separate User Pools would mean two JWT issuers, two sets of token validation logic, two audit surfaces, and double the Cognito configuration to maintain — with no architectural benefit. A single pool with two identity providers achieves the same authentication model at half the operational complexity. Cognito MFA is enforced for all users. SAML federation removes the need to manage internal user credentials separately from the corporate directory.

10.6. ADR-006: Compute — AWS Lambda + Aurora Serverless v2

Context: The workload is monthly peaks with near-zero baseline between reconciliation cycles (a few portal logins per week). Options: ECS Fargate (always-running containers), Lambda + API Gateway (pay-per-invocation), EKS (Kubernetes).

Decision: AWS Lambda + API Gateway for all compute; Aurora Serverless v2 for the database.

Rationale:

  • ECS Fargate rejected — cost is dominated by idle time between month-end peaks. Always-running containers (2+ tasks) cost ~$380/month even when serving near-zero traffic. Lambda charges only for invocations, reducing API compute to ~$40/month at this request volume.

  • Aurora Serverless v2 chosen over RDS fixed-instance — scales to near-zero ACUs (0.5 ACU minimum ≈ 1 GB RAM) between peaks. At month-end, it scales automatically to handle concurrent eligibility computations without any capacity planning. RLS, pgaudit, and the hash-chain audit ledger work identically on Aurora PostgreSQL-compatible. Monthly cost: ~$200 vs ~$480 for RDS db.r6g.large.

  • Lambda 15-minute limit mitigated — eligibility computation for typical counterparty files (10K–100K individuals) completes within minutes. For very large files (>500K), the engine splits input into batches and Step Functions fans out parallel Lambda invocations. At initial scale, a single invocation suffices.

  • EKS rejected — operational overhead of managing a Kubernetes cluster is not justified for a 6-person team with a monthly-peak workload.

10.7. ADR-007: Contract Rules — Structured Expression Tree

Context: The platform must accept contract definitions as structured metadata without constraining contract authors to a rigid schema that breaks when a new contract type is introduced. Options: flat JSON with code-per-contract, expression tree with generic evaluator, embedded DSL (e.g. SpEL/MVEL), Rete-based rule engine.

Decision: Contract rules stored as a structured expression tree evaluated by a generic engine. Validated against a versioned JSON Schema at upload time. See the Eligibility Engine — Rule Schema section for the node type taxonomy and decimal precision approach.

Rationale:

  • Flat JSON rejected — breaks when a contract has stepped rates by age band, multi-condition eligibility, or annuity factor tables. Every new contract type would require a code change.

  • Expression tree chosen — the engine evaluates eligibility and compensation rules as tree structures without contract-specific code. New node types are added once to the evaluator, then usable across all contracts. A schema_version field ensures reproducibility.

  • Embedded DSL (SpEL/MVEL) rejected — creates a security risk (arbitrary code execution) and makes audit reproducibility harder.

  • Rete-based rule engine (Drools) rejected — operational overhead not justified at this scale.

10.8. ADR-008: Adjustment Reconciliation — Snapshot-Based Model

Context: Corrections from prior months are folded into subsequent cycles as explicit adjustment records. When month 3 adjusts month 1, and month 5 adjusts month 3’s adjustment of month 1, the platform must define how multi-generation adjustment chains affect eligibility calculations and audit reproducibility. Options: delta-based (each adjustment is a differential applied to the prior result) or snapshot-based (each adjustment is a self-contained recalculation from the original data).

Decision: Snapshot-based adjustment model. Each adjustment record triggers a full eligibility recalculation using the original cycle’s data files plus the adjustment parameters. The result is a complete, self-contained eligibility snapshot — not a delta applied to the prior result.

Rationale:

  • Delta-based rejected — applying sequential deltas requires replaying the full adjustment chain to reconstruct the current state. If any intermediate delta is incorrect, all downstream deltas propagate the error. Debugging requires understanding every delta in the chain, which reintroduces the same person-dependent knowledge problem the platform is designed to eliminate.

  • Snapshot-based chosen — each adjustment produces a complete result that can be verified independently. An auditor reconstructing the state of a contract at month 3 reads a single ELIGIBILITY_COMPUTED event with full inputs and outputs — no chain replay required. The adjustments table’s prior_cycle_id and root_cycle_id fields provide traceability back to the originating cycle, but the eligibility result at each generation is self-contained.

  • The generation field on the adjustments table tracks the depth of the chain (generation 0 = original, generation 1 = first correction, etc.). The ELIGIBILITY_COMPUTED audit event payload includes the root_cycle_id and generation so the full correction history is traceable from any point in the chain.

  • Trade-off: snapshot recalculations are more compute-expensive than deltas, but at monthly cadence with Lambda’s pay-per-invocation model, the cost is negligible.

10.9. ADR-009: Contract Version Locking at Cycle Opening

Context: Contract rules can be updated between reconciliation cycles (e.g. renegotiated terms, corrected parameters). If a contract version changes after a counterparty has uploaded files but before the cycle is signed off, the platform must determine which rule version applies.

Decision: Eligibility computation is locked to the contract version that was active at cycle opening time. The reconciliation_cycles table records a contract_version_id at cycle creation. Mid-cycle contract changes apply to the next cycle only.

Rationale: Both parties' expectations for a cycle are set when the cycle opens. Applying a mid-cycle rule change would invalidate work already reviewed by the counterparty and create a dispute trigger. The locked version is recorded in the audit ledger alongside every ELIGIBILITY_COMPUTED event, ensuring reproducibility. If a rule correction is genuinely needed for the current cycle, the existing flow supports it: close the current cycle as voided, open a new cycle with the corrected contract version, and re-upload files — all captured in the audit trail.
